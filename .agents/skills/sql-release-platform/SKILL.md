# SQL 发布执行台技能

## 目标

把本系统视为已经稳定运行的个人运维工具。修改时优先保持原有行为，只做范围明确、可以验证的调整。既支持维护已有项目，也支持使用本 Skill 内置的安全模板从零重建项目。

## 定位项目

当前工作目录同时包含 `main.py`、`config.py` 和 `templates/index.html` 时，直接把它作为项目根目录；否则向上或在工作区中查找同时包含这些文件的最近目录。不要写死某台电脑的项目绝对路径，因为本系统需要在不同环境间迁移。

修改前先检查 `git status`、目标文件和相关实现。不要覆盖用户已有但与当前任务无关的修改。不要在回复、日志或提交中暴露密码。

## 按任务读取资料

- 修改后端、接口、配置、存储、SSH/SFTP 或项目结构前，读取 `references/architecture.md`。
- 修改 SQL 选项、`224.sh`、上传、清理、执行、远程日志、状态判断或 MD5 规则前，读取 `references/business-rules.md`。
- 修改 HTML、CSS、JavaScript、弹窗、颜色、响应式布局或页面文案前，读取 `references/frontend-ux.md`。
- 处理启动、部署、兼容性、诊断、日志或发布前，读取 `references/operations.md`。

## 安全修改原则

1. 修改前先复现问题，或者检查用户描述对应的现有行为。
2. 找到实现该行为的最小后端和前端范围。
3. 除非用户明确要求破坏性调整，否则保持现有接口地址和返回字段兼容。
4. 保持 Python 3.8.2 兼容。不要使用 `match`、`list[str]`、`A | B` 等高版本语法，也不要升级到不支持 Python 3.8 的依赖。
5. 页面提示和运维日志使用中文。只在代码不容易理解时增加注释，并尽量用 Java/Java Web 开发者熟悉的概念解释 Python。
6. 远程路径和脚本名称必须通过 `shlex.quote` 安全引用，不要把用户输入直接拼接到 Shell 命令。
7. 不要记录、输出、打包或提交真实密码。产品允许页面显示明文密码并保存到本地 JSON，但日志不得出现密码值。
8. 接口失败时返回包含 `ok: false` 和明确中文 `message` 的 JSON，同时记录异常和操作上下文。
9. 每次重要修改后验证 Python 语法、关键页面事件绑定和受影响接口。

## 新增或修改 SQL 选项

如果新 SQL 使用标准 `psql` 命令，并且只需要配置 SQL 文件名、远程 PG 地址和端口、数据库、账户、密码及独立日志，优先使用页面“常规 SQL”中的自定义配置，不再修改源码。自定义项按环境保存，最多 30 个。

只有需要特殊连接方式、固定产品选项或不同命令结构时，才按照下面步骤修改代码：

每个独立 SQL 文件按照以下步骤处理：

1. 在 `main.py` 的 `SCRIPT_BLOCKS` 增加一个唯一选项，配置页面标题、独立日志文件和精确的 `psql` 命令。
2. 在 `SCRIPT_ORDER` 的正确执行位置加入一次对应 key。
3. 在 `templates/index.html` 的临时 SQL 或常规 SQL 区域增加一个复选框。
4. 脚本名称始终从当前环境配置读取，默认值才是 `224.sh`。
5. 执行对应 SQL 前，把已经存在的当前日志备份到 `log/history`。
6. 每个 SQL 文件使用独立日志，不能把无关 SQL 输出合并到同一文件。
7. 分别使用单选和多选生成脚本，再通过 `/script-preview` 检查内容与修改时间。

精确映射以 `references/business-rules.md` 为准，不要凭记忆重新拼接命令。

## 修改页面

保持发布执行台和 MD5 页面属于同一套视觉体系：暖白背景、克制的青绿色操作按钮、清晰卡片、易读中文文字和受控页面宽度。除非用户明确允许调整布局，否则保留现有模块顺序和布局。

所有重要操作都要让用户看得明白：

- 上传完成后显示明确的成功或失败弹窗。
- 清理远程目录前必须确认，并展示环境名称和完整目标路径。
- “待上传文件数”使用醒目但不过度的颜色。
- 远程目录内容支持手动刷新。
- 长日志和大量 MD5 文件放在可滚动区域。
- 日志结果标签紧跟文件标题，不放到卡片最右侧。
- 不同日志标题使用不同颜色，方便快速区分。
- 保持桌面和移动端可用，不能让中文标题挤成一字一行。

## 排查远程执行失败

记录当前环境名称、主机、端口、用户、远程目录、脚本名称、安全引用后的执行命令、退出码、标准输出摘要和错误输出摘要。绝对不要记录密码。

按照以下顺序排查：

1. 当前环境配置和 SSH 连通性。
2. 远程目录是否存在、权限是否正确。
3. 配置的脚本名称对应文件是否存在，生成内容是否正确。
4. `cd <remote_dir> && bash ./<script_name>` 是否能在非交互 SSH 中执行。
5. `/pgsoft/pg14.7/bin/psql` 和根目录 SQL 文件是否存在。
6. 手工登录与页面执行时 PostgreSQL 环境变量、PATH 和权限是否不同。
7. Shell 退出码和对应远程日志内容。

## 从零重建

在 Skill 目录中执行：

```bash
python3 scripts/create_project.py --destination /新的项目目录
```

工具只允许写入不存在或为空的目标目录。创建后通过页面配置环境，或者复制示例配置文件。不要把真实运行密码复制进模板。

## 验证

在 Skill 目录中执行：

```bash
python3 scripts/audit_project.py --project /项目目录
```

同时执行项目已有的 Python 3.8 兼容测试。如果项目暂时没有自动化测试，至少完成：

1. 编译检查 `main.py`、`config.py`、`logging_setup.py` 和 `storage_utils.py`。
2. 执行 `python3 -m unittest discover -s tests -v` 离线回归测试。
3. 启动后确认 `/`、`/md5`、`/md5/local`、`/md5/remote` 可以访问。
4. 使用成功和失败样例验证本次修改涉及的接口。
5. 确认密码、运行配置和日志仍然被 Git 忽略。
6. 明确说明哪些远程操作因环境限制没有实际执行。

- `references/architecture.md`：组件、文件职责、状态存储和接口清单。
- `references/business-rules.md`：SQL、上传、执行、日志和 MD5 精确规则。
- `references/frontend-ux.md`：页面视觉语言和交互约束。
- `references/operations.md`：启动、迁移、排错、验证和发布流程。
